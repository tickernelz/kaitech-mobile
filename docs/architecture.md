# Architecture

## Server client (`src/api`)

`bearer()` calls the `/kaitech_mobile/*` routes with the device token. `rpc()` calls Odoo model methods through `/web/dataset/call_kw` using a session from `POST /kaitech_mobile/session`: the session is kept in memory per account, renewed a minute before it expires or once when the server answers that the session expired, and sent as the `session_id` cookie with `credentials: 'omit'` so the built-in cookie jar is not used. The `lang` context follows the app language, so server-made labels (statuses, agenda titles) appear in the same language. Server errors are mapped to stable codes (the route's `error_code`, or `forbidden`, `not_found`, `refused`, `server` from Odoo exceptions); their user-facing texts are in the catalogue. A 401 token marks the end of the session. `useResource()` keeps results per account in memory, refreshes them when the screen regains focus if they are stale, and is cleared when the account signs out.

Connection states (`src/api/network.ts`, `src/ui/Banner.tsx`): MoM and Discovery tell empty, failed and offline apart the way the Chat list does. With nothing loaded, offline shows "No connection" instead of the empty text and a failed load shows the error with Retry. With loaded data on screen, offline adds a banner saying the data is what was loaded last, and a failed refresh adds a banner with Retry. `useConnection()` reads `expo-network` (offline when not connected or the internet is unreachable) and refreshes the screen once when the connection returns.

Large text: from a font scale of 1.5 the Chat list filter chips wrap instead of scrolling sideways, the attach sheet shows two sources per row, and the thread title may take two lines (`useLargeText()` in `src/layout/windowClass.ts`).

## Discovery (`src/features/discovery`)

Every read uses the same methods as the web screens (`chat_contexts`, `programme_panel`, `fetch_transcript`, `read_packets`, `briefing_for_me`, `search_read` on `ck.evidence`, `ck.finding`, `ck.finding.side`), so Odoo access rules decide the contents. Writes go only through `/kaitech_mobile/discovery/ask` (an idempotency key per question; a resend uses the same key) and `/discovery/answer` (agree or not on a card waiting for a person's confirmation); the phone does not create cards. Coworker answers are shown as they are; its tool steps are folded into one line. The transcript is re-read every 2.5 seconds only while the turn is still running, the screen has focus, and the app is active. Question drafts are stored per Programme and conversation outside the screen tree, so they survive rotation or a window size change, and are deleted when the account signs out.

In an expanded window (840 dp and up) the Programme home and the Coworker thread appear side by side, findings on the left and their evidence on the right, a card from a notification on the right with other open cards on the left. `routeForPush()` maps the `discovery_card`, `discovery_card_restated`, and `discovery_answer` pushes to the card or thread screen.

## Chat (`src/features/chat`)

The conversation list comes from `GET /kaitech_mobile/chat/conversations`; messages, sending, read marks, typing, reactions, and threads go through Odoo Discuss routes (`/discuss/channel/messages`, `/mail/message/post`, `/discuss/channel/mark_as_read`, `/discuss/channel/notify_typing`, `/mail/message/reaction`, `/discuss/channel/sub_channel/*`) using `route()` from `src/api/odoo.ts`, so the Odoo access rules are the same as on the web. Live updates go through `/websocket` with the same session cookie; the socket is open only while the app is active and, after reconnecting, the app fetches the messages it missed.

Sending always goes through a SQLite queue (`chat.db`, table `outbox`): every message carries a `kaitech_chat_send_key` and every file an upload key for `/kaitech_mobile/chat/upload`, so a resend after a lost response does not create a second message or file. The queue is ordered per account: a network failure holds the queue and retries with a backoff of up to 30 seconds or as soon as the network returns; a server rejection marks that message failed (Try again or Delete) without holding the next messages. Files about to be sent are copied to the app's documents folder until they are sent.

A message being sent keeps one row in the thread from the tap until the server copy replaces it: the row key is `p-<send key>` while it waits and stays `p-<send key>` after the server message arrives (`sent` in the chat store maps the message id to its send key, `src/features/chat/rows.ts`), and its day header key follows it. The post carries `temporary_id` = the send key, so when the server announces the new message on the bus before the post answers, the queue entry is confirmed and dropped at once instead of showing the queued bubble and the server bubble together. The queue hands a sent message to the store before it removes the queued row, so no frame shows neither. The thread renders 1000 px beyond the screen (`drawDistance`), so a fast fling on a slow phone shows less empty space before the cells mount; a larger distance made opening a thread take twice as long on the Mblu 21. Cells are recycled only between rows of the same shape (`rowType`: text by Markdown shape, notice, call notice, and each attachment kind), and a call recording card keeps the answer for its recording per account, so a recycled cell never shows another recording or a loading line that changes its height. Messages, conversations, and drafts (per conversation, surviving rotation or a window size change) are stored per account and deleted when the account signs out.

Attachments in a bubble follow WhatsApp. A picture is a tile in its own shape (`/web/image/<id>/<width>x0`, resized by the server and kept by the image cache), a video is its first frame with a play button and its length, a PDF is a card with its first page, page count and size, and any other file is a card with an icon for its kind (document, sheet, slides, archive, text, audio), its extension and size, and a download control that shows progress, cancels, and offers retry after a failure. The width, height, length, page count and server thumbnail come from the attachment record when the server sends them (`kaitech_mobile_width`, `kaitech_mobile_height`, `kaitech_mobile_duration_ms`, `kaitech_mobile_pages`, `has_thumbnail`); otherwise the phone measures them once and keeps them in `media.json` beside the files. `modules/kaitech-media` reads a video frame and its length with `MediaMetadataRetriever` (Android) or AVFoundation (iOS), streaming from `/web/content` with the session cookie, and draws PDF pages with `PdfRenderer` or PDFKit; a PDF up to 10 MB is downloaded for its preview unless the server already drew one, larger ones wait for a tap. Tapping a picture or video opens `/media`: every picture and video of the conversation in one pager with pinch and double-tap zoom, the video streaming with the session cookie (on a playback error it offers to download first, with progress), and Share and Save (to the gallery through `expo-media-library`). Tapping a PDF opens `/pdf`, which downloads it with progress and cancel and draws each page on demand. Everything is stored under `cache/chat-opened/<account>/<attachment>-<checksum>/` (files, `.preview/` frames and pages) and deleted when that account is forgotten; a measurement that finishes after the account signed out is dropped. Coworker replies and returned files use the same bubble, so they get the same previews.

Voice messages: hold the microphone button to record (AAC `.m4a`), release to send, slide left to cancel. Microphone, camera, and notification permissions are requested when the feature is first used; the notification permission is requested after the first message is sent.

Android push goes through FCM when the build carries `GOOGLE_SERVICES_JSON`; the token and the device language are registered at `/kaitech_mobile/push`, and tapping a notification opens its conversation (`res_id`) or a Discovery screen through `routeForPush()`. iOS without APNs: new messages only arrive while the app is open, and the conversation list says so.

In an expanded window the list is on the left (360 dp) and the conversation on the right; in compact and medium windows the conversation opens as its own screen. In medium and expanded windows the Enter key on a physical keyboard sends the message; in compact windows Enter makes a new line. When the app lock is on, the preview in the recent apps list is blanked (Android `FLAG_SECURE` while the app is in the background, an iOS blur layer).

Message bubbles follow WhatsApp: your own on the right, everyone else's on the left, each as wide as its content and at most 80% of the message lane. The lane is the conversation width minus 16 dp on each side, capped at 720 dp and centred like the composer, so a bubble never grows past 576 dp. In a group the sender's bubble takes at most 80% of the space beside the avatar. A message still sending or failed keeps the width it will have once sent (ZHA-7809).

Message actions follow the lab0 web (Odoo Discuss and `kaitech_chat`). The app reads `kaitech_chat_features`, the admin status, and `kaitech_chat_can_make_task` from `/web/session/get_session_info` (`storeData`), so an action the server turns off also disappears on the phone. A long press on a message opens one sheet: an emoji row (the button at its end opens the full emoji picker from Odoo's CLDR data), then Reply, Copy, Forward, Edit, Delete; More holds reply in thread, pin, star, mark as unread, copy link, translate, make a task, make an activity, schedule a meeting, and who reacted. The rules for who may do what are in `messageOptions()` (edit and delete for the author or an admin, delete closed after 24 hours when `recall_limit` is on). Edit uses the composer; the draft being typed is saved and restored after the edit. Reactions are read from Odoo 19's `MessageReactions` store.

The `signed-in/message-actions.yaml` flow sends one test message, then pins it, stars it, reacts through the emoji picker, edits it, forwards it, makes an activity, copies the link, deletes a second message, tries to star in airplane mode (a failure message must appear), then checks the results on the server through a web account (`scripts/actions-peer.js`). Extra variables: `-e FORWARD_TO=<name of the target test conversation>`; `-e MAKE_TASK=yes` and `-e MEETING=yes` only for a test account with Project and Chat rights.

The conversation header holds only the title, calls, and one More button. Its sheet holds notifications (mute and level: all, only when mentioned, none), search in the conversation, pinned messages, files, threads, members (owner and admin roles, invite people), scheduled messages (send now, edit, delete), schedule a meeting, pin the conversation, automatic translation, announcement mode, rename or name and description, background, mark all as read, leave or hide, and delete thread. The composer row is, left to right: attach, the text field with the emoji, sticker and GIF button at its right edge, the camera, and one round button that is a microphone while the field is empty or holds only spaces and turns into Send as soon as there is text or a staged file. The camera hides while there is text, as in WhatsApp; a long press on it opens the gallery. Mic and Send share one 44 dp slot and cross-fade, and the camera slot animates its width, so the row never changes height and the keyboard stays open; with reduce motion on, they switch without animation. The design follows the spec `spec-ui-composer-mobile` (ZHA-7846).

Voice notes are one state machine (`src/features/chat/voice/machine.ts`): hold the mic to record, release to send, slide left 96 dp to cancel, slide up 64 dp to lock; the direction locks after 12 dp so cancel and lock never both fire, and a hold under 1 s is dropped with a hint. The red dot, timer and haptic start only once the recorder reports `isRecording`. A locked recording shows discard, a live waveform and pause; paused shows a draft that can be played and scrubbed, resume continues the same note, and send joins the segments with the `kaitech-voice` native module (MediaMuxer on Android, AVAssetExportSession on iOS). Going to the background, a call, the 30-minute limit or a reset audio device pause instead of sending, and the draft stays on disk under `chat-voice-draft/<account>/<channel>/` until it is sent or discarded; it comes back when the chat opens. Discarding animates into the bin and can be undone for 5 s. Recording is AAC mono 64 kbps with metering, and 64 waveform values go with the upload for the bubble (ZHA-7850). With a screen reader on, one tap records hands-free. In the bubble, tap or drag the waveform to seek; the speed is kept per account, the position per message for the session, others' unplayed notes carry a dot, the next unplayed note plays 400 ms after one ends, and a mini player under the chat list and other threads keeps playback going out of the chat and on the lock screen.

The field button replaces the keyboard with a panel of the same height (260 to 360 dp; drag or fling the handle for full height), with tabs for emoji, stickers and GIFs; the last tab, recent emoji and skin tones are kept per account. Emoji scroll as one list with sticky category headers, a long press picks a skin tone, and search also offers Kaitech stickers and a link into GIFs. Stickers show favorites, recent and each pack, plus KLIPY stickers; GIFs show trending, category chips and search in a masonry grid, and a long press previews. Only visible animated items play (at most 8, through `expo-image`), and KLIPY media is cached in memory only in the panel. Loading, offline, empty, server and not-configured states come from the server refusal codes (`gif_unavailable`). Stickers and GIFs come from the `kaitech_chat` routes (`/kaitech_chat/stickers`, `/kaitech_chat/gif/*`; the provider key stays on the server) and are sent as `kaitech_chat_sticker` or `kaitech_chat_gif` through the offline outbox with the same send key as text; the bubble shows a sticker without a frame and a GIF with a GIF badge. Android needs `expo.webp.animated=true` (`plugins/with-animated-webp.js`) to play animated WebP stickers. In the thread a sticker or GIF plays only while its bubble is on screen and the app is in front (`src/features/chat/ui/visible.ts`, fed by the thread's viewable rows); off screen a sticker shows its still `poster` and a GIF its `preview`. A GIF plays its MP4 muted and looping through `expo-video` (a 320 px KLIPY MP4 is a fraction of the GIF file), falling back to the GIF only when there is no MP4. Bubble sizes come from the width and height in the payload, so nothing jumps when media loads. Pack stickers, GIF stills and map tiles go to the `expo-image` disk cache, which Glide on Android caps at 250 MB; GIF MP4s use the `expo-video` cache (`useCaching`), set to 100 MB instead of its 1 GB default.

Polls, locations and live locations follow the server contract `api-contract` of ZHA-7806 (`kaitech_chat` 19.0.1.33.0 and later). The attach sheet lists Location and Poll between Document and Audio. A poll is a question, 2 to 12 distinct options of up to 100 characters and a "more than one answer" switch (`pollProblem()`); it goes through the outbox like text. The bubble shows each option with its count and a bar, a tap votes (`/kaitech_chat/poll/vote` with the whole new choice, an empty list retracts), the vote shows at once and is put back when the server refuses (a closed poll, offline), View votes lists who chose what, and the author can close it. Every device updates from the `mail.record/insert` the server broadcasts; the server decides who may vote and whose vote it is.

The location picker is a full-screen map drawn by the app itself (`TileMap`, Web Mercator in `src/features/chat/geo.ts`): 256 px OSM tiles from `GET /kaitech_chat/map/tile/<z>/<x>/<y>.png` with the session cookie, pan, pinch, double tap and zoom buttons, so no map SDK, native view or API key is added. It asks for the location permission through the Kaitech permission card first, then offers the current position (with its accuracy, refined while the picker is open), a point dragged under the pin (named through `/kaitech_chat/map/reverse`) or a search result (`/kaitech_chat/map/search`). The bubble shows the server's static map (`/kaitech_chat/location/<id>/map?seq=<n>&size=s`, cached per `seq`), the place name or address, and opens `/place`, a full map with Open in maps app (`geo:` on Android, Apple Maps on iOS). Map data © OpenStreetMap contributors (ODbL) is shown under every map.

Live location: the picker offers 15 minutes, 1 hour or 8 hours. Once the server accepts the message, `src/features/chat/live.ts` keeps the share per account in `chat.live.<account>` and starts `expo-location` background updates as an Android foreground service (type `location`) with a notification and a Stop action; Stop opens the app through `kaitech-live-location://stop` (`+native-intent.tsx`), which stops every share on the server. Updates use high accuracy every 30 s; the app posts `/kaitech_chat/location/update` only when the phone moved 20 m or 2 minutes passed, never within 5 s (the server limit), and drops a share the server answers as ended, expired or not found. The service stops when no share is left. On start and whenever the app comes to the front, `/kaitech_chat/location/active` prunes shares the server ended; shares started on another device are never fed by this phone. The service runs only while a share is running and needs no background location permission. Signing out or removing the account stops its shares on the server first, while the account's token still works (`beforeAccountLeaves` in `src/auth/session.ts`, at most 4 s), then forgets them on the phone. Coordinates are never logged by the app. iOS: background updates are not configured (no `UIBackgroundModes` location), so the share sends only while the app is open; this is unverified on an iPhone until there is an Apple Team ID (ZHA-7277).

The conversation list, reply quotes and the reply bar show a short label for these kinds (Poll: question, Location: place, Live location, Sticker, GIF), and Android push notifications draw the same labels from `msg_type` in the reader's language.

The attach sheet has Gallery (system photo picker, up to 30), Camera, Document, Location, Poll and Audio; below them sit canned responses (also by typing `::`), send later, and urgent with the remaining daily quota. The round button on the list opens the New sheet (when the window is shorter than 480 dp, such as a phone in landscape, a pencil in the app bar replaces it so it never covers a row; in portrait the list ends with room for the button): one person opens a chat, more than one creates a group, or a named channel (which can be an announcement channel). Coworker replies show decision cards and Wardmote cards, links to tasks, projects, Programmes, meetings, emails, and recordings show as cards, a thin bar under the header shows the Coworker work in progress, and a conversation linked to a Project or Programme shows its link bar. Every item follows the same `kaitech_chat_features` flags as the web.

The `signed-in/thread-actions.yaml`, `signed-in/composer-extras.yaml`, and `signed-in/new-conversation.yaml` flows use the variables `-e GROUP=<test group> -e SEARCH=<word> -e PEER_SEARCH=<start of the web account name>`; `-e URGENT=yes` only when the test account's urgent quota may be used.

The `signed-in/chat.yaml` flow signs in when needed, opens the conversation with the web account, sends 25 messages, turns airplane mode on, sends 25 more messages, turns airplane mode off, then checks through the server that all 50 messages exist exactly once, read marks from the web, and two-way voice messages. Extra variables: `-e SERVER=<server address> -e DB=<database> -e WEB_LOGIN=<web account> -e WEB_PASSWORD=<password> -e CHANNEL_ID=<conversation id> -e PEER=<web account name> -e RUN=<unique marker>`. The time from tapping Send until the bubble appears is logged as `send_visible_ms`.

The `signed-in/chat-media.yaml` flow (chat cells of the `android` E2E mode) pushes a photo, a video, a PDF and a DOCX from `.maestro/assets/device/` into the emulator's Download folder (`scripts/e2e-android.sh`), sends them in one message through the system file picker, then checks the photo tile, the video length read from its frame, the PDF page count and first page, the document download, the video playing in the viewer, swiping to the photo, and the PDF reader's first page. Like the other signed-in cells it uploads screenshots only, no recording.

The `signed-in/chat-rich.yaml` flow (same cells) creates a poll from the attach sheet, votes, moves the vote, opens View votes and closes the poll, then sets the emulator position (`setLocation`), passes the Kaitech and system location prompts, sends the current location, opens it on the full map, starts a 15-minute live share and stops it from the bubble.

## Android: Material 3 (`*.android.tsx`)

Android follows Material 3 Expressive for shape and behaviour while colour, type and icons stay Kaitech (ZHA-7471). Every Android difference lives in a `.android.tsx` file next to the shared component, so iOS keeps its own behaviour; the iOS Liquid Glass work (ZHA-7469) uses the same seams.

- Colour: `src/theme/material.ts` builds the Material 3 roles from the seed `#441D65` (`scripts/material-scheme.mjs` writes `materialSeed.ts` with the Material SchemeTonalSpot algorithm), then sets primary, surfaces, outline, selection and error from the Kaitech tokens; `error` is `dangerInk` because `danger` on white is below 4.5:1. The wallpaper palette (Material You) never reaches the app.
- Navigation: phones get the floating Material 3 Expressive capsule (see Tab bar below) and tablets an M3 rail (`src/layout/NavRail.android.tsx`, 56 x 32 indicator, ripple on the indicator, badge on Activity), both React Native views laid out by `src/layout/PillTabs.tsx`, chosen by `src/layout/AppTabs.android.tsx`.
- No Jetpack Compose: `@expo/ui` linked into the APK cost about 300 ms of cold start on the Meizu Mblu 21 even with no Compose view on screen (ZHA-7439: 1163-1289 ms without it, 1485-1599 ms with it, v0.3.0 1160-1256 ms), so every Android control here is a React Native view. Route files are bundled for every platform (expo-router's `require.context` takes `_layout.android.tsx` into the iOS bundle too), so the tab layout picks its bar through `src/layout/AppTabs` instead of platform route files.
- Sheets: Sheet, ActionSheet (and the row More sheet) and FormSheet use the React Native bottom sheet on Android (scrim, 28 dp top corners, back and scrim close it).
- Controls: `Button`, `IconButton`, `TextField` (outlined, floating label) and `Fab` (56 dp, 16 dp corners, level 3 elevation) have Android versions; `src/ui/Pressable.android.tsx` gives every pressable the M3 ripple and, for those, drops the pressed styling the shared code draws, so a press shows one state layer; the ripple takes the content colour of the resting background (light on Kaitech purple or red, dark on light surfaces), as M3 state layers do.
- Type, shape and motion: Android maps the type roles to the M3 scale (titles stay Plus Jakarta Sans) and the small and medium corners to 8 and 12; `spring` in `src/theme/motion.ts` holds the M3 Expressive springs and every animation skips under reduced motion.

## Top app bar and pull to refresh (`src/ui/AppBar.tsx`, `src/ui/Refresh.tsx`)

Chat, Discovery, MoM and Activity share one top app bar on Android and iOS: a 64 dp row right under the status bar with the screen title on the left and the screen's actions (Search, profile, screen menus) on the right, the size of the Material 3 small top app bar. No large title scrolls with the list, so the first content starts 8 dp under the bar. The bar sits above the list, never over it, so rows under it keep their touches; it takes the surface-container tint once the list scrolls under it (ZHA-7730).

Every pull to refresh goes through `Refresh`, a `RefreshControl` in the Kaitech primary colour whose `progressViewOffset` (48 dp) starts the Android indicator 8 dp inside the list instead of one 40 dp diameter above it, so the circle is whole at every pull depth and never covers the bar. iOS draws its spinner in the space the pull opens inside the list. ESLint refuses `RefreshControl` imported from `react-native` outside `src/ui/Refresh.tsx` and `onRefresh` on a list or scroll view.

## Touch targets (`src/ui/touch.ts`)

Every control a finger can tap is at least 44 by 44 dp (ZHA-7965, from the ZHA-7947 audit). A control drawn smaller, such as a 36 dp filter chip, a 32 dp GIF chip or emoji category, a 32 dp reaction or a 28 dp voice speed button, keeps its look and takes `hitSlop={reach(height, width)}` (or `chipSlop` for 36 dp chips), which adds the missing dp evenly on each side; `reach(height)` alone adds height only, which is what a chip wider than 44 dp needs. Two rules decide how far a reach may go. React Native on Android tests siblings from the last one drawn to the first (`TouchTargetHelper`), so a reach that covers an earlier neighbour takes taps meant for it: keep each side within the gap to an earlier neighbour, and when a control sits right under another one, use `reachBelow(height, gap)`, which reaches up only to the gap and takes the rest below. A later neighbour, including the next row of a wrapping list or the next message in a chat list, wins any area the reach overlaps, so the reach must stay inside the control's own row: give wrapping chips a row gap of both reaches (`chipRowGap`) and put a reach below the last row inside padding of its own view. A `ScrollView`, or any parent with `overflow: 'hidden'`, drops touches outside its bounds, so a chip strip inside a `ScrollView` gets the reach as padding inside and as a negative margin outside (`band(height)`, `chipBand`), and the layout does not move; a parent without clipping needs no band. A settings row with a switch (`ToggleRow` in `src/ui/List.tsx`) is one control: a tap anywhere on the row flips it, and a screen reader hears one switch with the title, the hint and its state. Before adding a control smaller than 44 dp, give it `reach` or a 44 dp minimum height; `uiautomator dump` shows drawn bounds only, so a probe of a slop-extended control taps just outside its drawn edge.

## Bottom and top insets (`src/ui/insets.ts`)

Padding that clears the gesture pill, the three-button navigation bar or the status bar comes from `useBottomInset(gap, keyboardVisible)` and `useTopInset(gap)`: the system inset plus the component's own gap (8 dp under the chat composer, 16 dp under sheets), never the larger of the two, so content keeps its gap above the pill and the buttons (ZHA-7854). While the keyboard is up the bottom inset is dropped, because the keyboard already covers the navigation bar and a `KeyboardAvoidingView` already lifts the sheet by the keyboard's full height. Screens built on `Screen` get the inset from `SafeAreaView` and a 16 dp gap under scrolling content. The pill tab bar and the undo bar already add their gap to the inset.

## Tab bar (`src/layout/PillTabs.tsx`)

On phones (compact windows) the tabs sit in a capsule that floats at the bottom of the screen (ZHA-7950): 64 dp high, 16 dp from the screen sides (at most 440 dp wide) and 8 dp above the gesture pill or the navigation buttons. Android and iOS each have their own look on the same Kaitech colours; medium and expanded windows keep the rail (`src/layout/NavRail.android.tsx`, `src/layout/NavRail.tsx`) and no capsule.

- Shared logic: `src/layout/usePillBar.ts` owns everything both looks need: which tab is selected, the selected position as one reanimated shared value (M3 `spatial` spring), the press state, hiding the bar while the keyboard is up, the light haptic on a switch (`selectionAsync` on iOS, `Virtual_Key` on Android), the Activity badge text and spoken count, the capsule width and `pillCover`. `src/layout/PillBadge.tsx` pops the badge when it appears or its number changes.
- Android (`src/layout/PillBar.android.tsx`, Material 3 Expressive): a tonal `surfaceContainer` capsule; the selected tab opens into a wide slot (40% of the capsule) with its label beside the filled icon on a `secondaryContainer` indicator, the other tabs show their line icon. The indicator changes shape: it stretches sideways and flattens while it travels to the next tab and squeezes while a tab is held; every press also gets the M3 ripple. The icon swaps from line to fill when the tab is selected instead of cross-fading, so each tab draws one icon.
- iOS below 26 (`src/layout/PillBar.tsx`, following the Liquid Glass tab bar of iOS 26): every tab has an equal slot with its icon above a small label, and a `select` lens slides under the selected tab and swells slightly while it moves or while a tab is held; the selected tab switches to the `selectInk` fill icon and label. iOS 26 and later keep the system bar (see iOS 26+ below).
- See-through: the capsule is slightly transparent so content shows under it while it scrolls: Android `surfaceContainer` at 92% and iOS `surface` at 82%, both with a hairline outline and no shadow: a shadow under a transparent surface shows through it, and on iOS React Native builds a cheap shadow path only for an opaque background, so a translucent one falls back to a per-pixel shadow redrawn whenever the lens moves. The solid fallback gets the shadow back (Android level 3 elevation, iOS a soft drop shadow). Both use plain alpha, not a blur: a blur needs a native module (`expo-blur`) that the iOS below 26 path cannot be checked with (no device, and CI simulators run iOS 26), and on Android a live blur redraws every frame on the GPU that ZHA-7946 is already short of. `useSeeThrough()` in `src/ui/glass.ts` turns the capsule solid when Reduce Transparency or Increase Contrast is on on iOS or High contrast text is on on Android, and until those settings are known.
- Motion: only transforms and opacity animate, all on the UI thread, so a frame never relayouts. The incoming tab screen fades in from 98% scale over 240 ms (`easing.expo`) on the canvas colour, so nothing flashes white; the first tab at launch does not animate. Reduce Motion turns every one of these into an instant change. The Android geometry lives in `src/layout/tabBar.ts` as worklets (`slotLeft`, `glyphLeft`, `openness`); `__tests__/pill-tabs.test.tsx` covers both looks.
- Touch and reading: transparent `Pressable` slots sit over the drawn layer with the same widths, so a tap lands on the tab drawn under it; the drawn layer is hidden from accessibility, each slot is a `tab` with its selected state, and Activity says its pending count in the label. While the keyboard is up the capsule slides down and takes no touches.
- Space under content: the capsule floats over the tab screens, so content that scrolls or floats at the bottom of a tab screen adds `useTabBarSpace()` (the height the capsule covers from the screen bottom, `pillCover(insets.bottom)`; 0 on the rail, on iOS 26+ and outside the tabs) to its own gap: the Chat list, Discovery home, MoM home and both Activity lists; the `Fab` clears the larger of that space and the bottom safe area, so it also stays above the navigation buttons next to the rail. The undo bar over the tabs uses `pillCover` too. A new tab screen must do the same, or its last row and its buttons sit under the capsule.

## iOS 26+: Liquid Glass (`*.ios.tsx`)

On iOS 26 and later the app takes the system Liquid Glass look for navigation and floating controls while colour, type and icons stay Kaitech (ZHA-7469). Content (bubbles, cards, lists, backgrounds) stays opaque. iOS below 26 and Android keep their own look.

- Choosing the surface: `src/ui/glass.ts` `useSurface()` returns `glass` only when `isLiquidGlassAvailable()` (expo-glass-effect) is true and both Reduce Transparency and Increase Contrast are off; it returns `solid` until those settings are known and follows them while the app runs. `src/ui/FloatingSurface.tsx` draws regular glass, clear glass over a photo, video or shared screen (`overMedia`), or the given solid colour. The undo bar, the chat composer field, the call control pill and the Search and profile pair in the header use it.
- Tab bar: `src/layout/AppTabs.tsx` renders `src/layout/GlassTabs.tsx` (expo-router `NativeTabs`, the system tab bar) on iOS 26+ and the pill tab bar (`src/layout/PillTabs.tsx`) otherwise. The system bar is already a floating Liquid Glass capsule and does its own selection morph, which a React Native view cannot match, so iOS 26+ keeps it; `minimizeBehavior` stays at the system default, because shrinking the bar while scrolling hides the tab labels in an app where switching tabs is the main move. `useTabBarSpace()` is 0 there: react-native-screens gives the first scroll view of each tab the automatic content inset, and expo-router wraps each tab in its own safe area, so the `Fab` (which clears the larger of the pill space and the bottom safe area) should sit above the system bar; neither has been seen on a device yet (no signed-in iOS build, ZHA-7277). The icons are the Kaitech line and fill glyphs written as template PNGs by `scripts/tab-icons.mjs`; the selected tint is the brand purple for light and dark (`DynamicColorIOS`), and Activity carries the pending badge (`badgeText`, capped at 99+).
- Sheets: `src/ui/NativeSheet.ios.tsx` presents Sheet, ActionSheet (and the row More sheet) and FormSheet as a native form sheet from `react-native-screens/experimental`, sized to its content with a grabber. An action chosen inside runs after the sheet has gone, so a follow-up sheet never presents over a closing one, and only the first action tapped while the sheet closes runs. The native host is compiled only when the Podfile sets `RNS_GAMMA_ENABLED`, which `plugins/with-native-sheets.js` writes; without it every sheet on iOS 26+ would render a component that is not in the build.
- Header: iOS has no header of its own; the tab screens keep the title in one row with Search and profile (the header layout belongs to ZHA-7730), and on iOS 26+ the Search and profile pair sits on one interactive glass capsule (`src/screens/HeaderActions.tsx`).

NativeTabs, expo-glass-effect and the native form sheet need a development or CI build; Expo Go does not carry them.

## Dialogs, snackbar and permission cards (`src/ui/dialog.ts`, `src/ui/Dialog.tsx`, `src/ui/permission.ts`)

The app draws every dialog itself, the same on Android and iOS, in the Kaitech colours of the current light or dark theme (ZHA-7789). `src/ui/dialog.ts` holds the calls: `confirm` (a destructive variant with `danger: true` paints the confirm button red), `inform` (one button), `choose` (several choices plus Cancel), `prompt` (a text field; `required` keeps the confirm button off while it is empty) and `notify`, a one-line message in the snackbar at the bottom (the same bar as Undo, testID `snackbar`). Each returns a promise, so the code that deletes, signs out or calls the server runs only after the answer. The Android back button, a tap outside the card and Cancel all answer no. Dialogs queue and show one at a time; they wait while the app lock is on.

A dialog is drawn by the topmost dialog layer: the root layout, every native modal route (settings, person, add account, call, recording, and the MoM record, sign, remove, final tool and follow-up form routes), every `Overlay` (the only allowed wrapper of React Native `Modal`) and the iOS native form sheet each mount one. On iOS a modal can only be presented from the screen on top, so this keeps a dialog asked from inside a sheet or a settings page visible; on Android the dialog is its own window either way. A route presented as a native modal must render `<DialogLayer />` itself: without it a dialog asked there is presented from the screen under the modal, which iOS refuses, and the promise never settles. `__tests__/modal-routes-dialog-layer.test.ts` fails for a modal route in any stack layout that does not mount one.

Known gap: a snackbar raised while a dialog is open is drawn in the screen under the dialog's scrim, because the dialog is its own modal window, and it can time out before the dialog closes.

TestIDs: the `testID` given to a dialog names the card, with `<testID>-title`, `-body`, `-input`, `-backdrop`, `-modal` and `-<choice>` (`-confirm`, `-cancel`, `-ok`, or the key given to `choose`). Every dialog in the app ends in `-dialog`, for example `sign-out-dialog-confirm`.

`eslint.config.js` rejects `Alert`, `ActionSheetIOS`, `ToastAndroid` and `Modal` from `react-native` in `src/` (only `Overlay.tsx` and `Dialog.tsx` import `Modal`).

Permission cards: `askPermission` shows a card that says what the camera, microphone or notifications are used for before the system prompt, so the system prompt only appears after Continue. When the system will not ask again, the card offers Settings instead, unless the screen shows its own notice (calls, MoM recording setup, notifications).

Still drawn by the system, because the app cannot restyle them: the permission prompts themselves (camera, microphone, notifications; the app asks for no location), the photo, camera and file pickers (`expo-image-picker`, `expo-document-picker`), the share sheet (`expo-sharing`, `Share`), the biometric prompt of the app lock (`expo-local-authentication`), the screen capture consent of screen sharing, and the browser tab used to sign in. On iOS 26 and later the sheets keep the system form sheet container (see iOS 26+: Liquid Glass); their content is the app's.

## Row actions (`src/ui/RowActions.tsx`)

Every list row (Chat conversations, Coworker conversations, Programmes, evidence, findings, Activities, MoM meetings, Search results) is wrapped in `RowActions`. A long press opens the More sheet with a short vibration; swiping right opens light actions (mark as read or unread, pin, rename, copy, share), swiping left opens archive, delete, or leave plus More. TalkBack gets every sheet action as a custom action on that row, and a More button appears at the end of the row when it has keyboard focus. Archive, remove from list, leave, and deleting a Coworker conversation disappear from the screen at once with an Undo snackbar; the server call is only sent after 5 seconds, on behalf of the account that asked for it. Deleting a MoM recording uses the server's conditions: only the uploader, by typing the title and the password.

Pin and archive on Chat conversations only appear when the server sends `pinned` and `archived` in the conversation list. Remove from list on a direct chat uses Odoo's `channel_pin`, so the conversation comes back when a new message arrives; leaving a group uses `action_unfollow`.

The `signed-in/rows-chat.yaml`, `rows-discovery.yaml`, and `rows-mom.yaml` flows create their own test data through the web account (a new group, an empty Coworker conversation, a short recording), then prove the long press, both swipe sides, Undo, and their effect on the server. Extra variables beyond those of `chat.yaml`: `-e PROGRAMME=<test Programme id> -e SEARCH=<word> -e HIDE_DIRECT=true` (the last one removes the direct chat with the web account and then waits for it to come back; only one cell may run it at a time).

In CI the job `android rows` runs those three flows on phone and tablet, id-ID and en-US, using the secrets `KAITECH_E2E_LOGIN`, `KAITECH_E2E_PASSWORD`, `KAITECH_E2E_WEB_LOGIN`, `KAITECH_E2E_WEB_PASSWORD` and the variables `KAITECH_E2E_CHANNEL_ID`, `KAITECH_E2E_PEER`, `KAITECH_E2E_PROGRAMME`, `KAITECH_E2E_SEARCH`. This job runs only in the full `E2E` run (nightly and manual) and, for tags, as `rows from release` in the `Release` workflow; never on pull requests. Because the repo is public, its output carries no recordings, app logs, or Maestro logs: only `junit.xml` files, device text files, `audio.txt` (the audio, media-recorder and recording-error lines of logcat, streamed for the whole run, nothing else from the app log), `scroll-gfxinfo.txt` (frame statistics of a Chat list scroll), flow screenshots, and screenshots of failed steps except the sign-in step (which could show the test account's login); when the server page never opens after `welcome-sign-in`, the flow takes `auth-page-missing` before failing (no field is filled yet at that point), and a failed cell keeps `signin.txt` (activity starts, Chrome and app process starts and deaths, ANRs, focus changes and Chrome warnings from logcat, plus the activity stack at the end, with URL queries and account values removed), and the job fails without uploading anything when one of the test account values is found in the output. All four cells use one test account, so full `E2E` runs use the concurrency group `kaitech-e2e-account` (`queue: max`): the four cells of one run run at the same time and another full run queues until it finishes; the release rows cells join the same group one cell at a time. Any other job that signs in with the same test account must use that group too; without it, calls, messages, and rows from the other job appear on the screen of the cell that is running (run 45011416923: an incoming video call from the call job of another PR covered the screen of three cells).

## MoM (`src/features/mom`)

The MoM tab reaches every screen of the web `kaitech_mom` addon by calling the same model methods through `rpc()`, so Odoo access rules, record rules and the client RPC allowlist decide what the account sees and may change. A button that changes data is shown only when the server's answer allows it (`canChange`, the account's groups, being the uploader); the server still refuses anything else, and its `UserError` text is shown as it is.

- Home: the meeting list per day, a status line for recordings still processing, and a More sheet with All recordings, All minutes, Removed recordings, Follow-ups, Client organisation and, for administrators, Circle import, Settings and MCP keys. Record setup also uploads an audio or video file from the device (moved into `Audio/` before it joins the upload queue) and, for internal accounts, imports a Lark Minutes link.
- Meeting: tabs Final, Items, Notes and Transcript; a More sheet with transcribe again, compare with ElevenLabs, departments, history, removal (title and password), My notes, Solusi, Tasks and, for client accounts, Ask Coworker.
- Transcript editor: filters, search, line sheet (play from here, correct and restore, flag, change speaker with a scope and Undo, use the ElevenLabs words), speakers and doubtful words. Filtering is memoised on the segments and rows are memoised, so typing in the search of a long transcript does not re-render the lines.
- Final: content, narrative, header, recipients, email, context before the meeting, export, finalise and distribute, sign and revoke a signature. Follow-ups: board with four views, add, progress, done, owner and due date, archive.

The recorder uses expo-audio with its foreground recording service, patched in `patches/expo-audio+58.0.12.patch`: upstream 58.0.12 registers the binding callback only after `bindService`, so when the service connects first (a busy device, measured on the CI emulator in runs 45120461891 and 45125882352) the connection is lost, `prepareToRecordAsync` fails after 5 s with `ERR_A3`, and the app shows "Recording couldn't start". The patch registers the callback and the timeout before binding and stores the service binder before resuming, so `record()` never sees an unbound service.

On iOS below 26, sheets with text fields sit in a `KeyboardAvoidingView`, so the keyboard never covers the field or its Save button. On iOS 26 and later every sheet is a native form sheet (see iOS 26+: Liquid Glass below), which UIKit moves above the keyboard itself; this is not yet proven in CI, because the sheets sit behind sign-in (ZHA-7277). On Android every sheet is the Compose `ModalBottomSheet` (see Android: Material 3 below), which takes the keyboard inset itself, so the field and its Save button stay above the keyboard without a `KeyboardAvoidingView`. The signed-in flows `.maestro/signed-in/mom-*.yaml` run in the full `E2E` run as `android mom` (after `android rows`, same account group); `.maestro/local/mom-writes.yaml` and `mom-first-record.yaml` write to the shared seeded meeting or need a fresh permission state and run only on a local emulator.
