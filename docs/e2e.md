# E2E

Maestro flows live in `.maestro/`. Run them locally on an emulator that already has the APK installed:

```bash
maestro test .maestro
```

In CI every flow runs twice, on emulators with the `en-US` and `id-ID` locales. `scripts/e2e-android.sh` changes the system locale (`persist.sys.locale`, then a framework restart), waits until the framework configuration uses that locale, installs the release APK, records the screen, then runs every flow with the `APP_LANGUAGE` variable (`en` or `id`) for the texts it checks, for example `${APP_LANGUAGE === 'id' ? 'Selamat datang' : 'Welcome'}`. Checking elements through `testID` is preferred. The `sign-in-form` flow opens the lab0 sign-in page from the Sign in button with no form, closes it with the Custom Tab's close button (`com.android.chrome:id/close_button`) and expects the cancelled message, then through "Use another server" checks an empty address or one without https and a wrong database name, rotates the screen to the other orientation and back without losing the field contents, and returns to the default. On Android it leaves the server field with Enter, as a user would; when the database field has no focus 5 s after Enter, `shared/next-field.yaml` presses Enter once more (ZHA-7589: one Enter in about 1,000 on the CI emulator reached the app without moving the focus or hiding the keyboard; the key is injected synchronously, so the first one is already handled when the second goes out). A tap on the database field is no fallback: on a phone in landscape the keyboard runs full screen and hides the form. A flow never leaves the browser with `back`: the key goes to whichever window has focus when it is delivered, and the browser runs in another task. In run 45260954596 (tablet landscape id-ID, ZHA-7633) one back took 1.3 s on a loaded emulator; the Custom Tab closed, the app came back, and the rest of the same key press reached the app, which handles back through predictive back (`predictiveBackGestureEnabled`) and finished its activity, so the launcher stayed in front. A tap stays with the window it started in.

Run locally: `maestro test -e APP_LANGUAGE=id -e DEVICE_SIZE=phone -e ORIENTATION=portrait .maestro`. All three variables must be passed through `-e`; do not give them defaults in a flow's `env:` block, because that value overrides `-e`.

## Shared local emulator

E2E, video recordings, screenshots, and the full suite run in GitHub Actions; take videos and images from the `e2e-android-*` artifacts of a green run at the SHA in question. The merge evidence for a changed journey comes from a physical phone instead (see [Physical phone](#physical-phone)). A developer PC runs at most ONE emulator for all runs at once, and only through `scripts/emulator.sh`:

```bash
scripts/emulator.sh run phone -- bash scripts/e2e-android.sh dist e2e-output/phone-portrait-en-US en-US phone portrait
scripts/emulator.sh run tablet -- sh -c 'maestro --device "$ANDROID_SERIAL" test -e APP_LANGUAGE=en -e DEVICE_SIZE=tablet -e ORIENTATION=landscape .maestro'
scripts/emulator.sh status
scripts/emulator.sh stop
```

- Two shared AVDs, `kaitech-phone` (`pixel_6`) and `kaitech-tablet` (`pixel_tablet`), Android 15 `google_apis` x86_64, created automatically on first use with the profile's default RAM, the same as CI. Do not create an AVD per task.
- The emulator runs on `emulator-5584` (inside the 5555-5585 range the adb server rescans after `adb kill-server`) with `-gpu host -read-only -no-snapshot -no-window -no-audio -no-boot-anim` as the user systemd unit `kaitech-emulator` (`Nice=10`, `CPUQuota=400%`, `MemoryMax=8G`). `-read-only` makes every boot clean.
- One `flock` lock at `$XDG_RUNTIME_DIR/kaitech-emulator/lock`: a run that arrives while another run uses the emulator waits its turn (or use CI). The launcher refuses to start an emulator (exit code 3) while any other emulator runs on the PC, including one started without the launcher, and prints the list.
- A live emulator of the same size is reused: the launcher runs `pm clear io.kaitech.mobile`, then your command with `ANDROID_SERIAL` pointing at that emulator, under `nice`. Another size stops that emulator first. `adb` follows `ANDROID_SERIAL`, Maestro does not: always pass `maestro --device "$ANDROID_SERIAL"`, because without it Maestro picks another connected device, including a physical phone over USB.
- The `kaitech-emulator-reap` timer is armed as soon as a run takes the lock and armed again after the command finishes. It checks every `KAITECH_EMULATOR_IDLE_MINUTES` (default 5) minutes and stops the emulator and itself once the lock is free, so a killed run (Ctrl-C, timeout, SIGKILL, OOM) does not leave the emulator running. `scripts/emulator.sh stop` stops it at once and exits with code 75 when another run is using the emulator; run it as soon as you are done.
- `KAITECH_EMULATOR_GPU=swangle_indirect` only to compare or when the host GPU misbehaves, with a written reason; software rendering is the emulator's largest CPU cost.
- CI does not use this launcher: GitHub runners have no GPU and keep `swiftshader_indirect`.

## Physical phone

E2E in GitHub Actions is not a merge requirement (see [the merge gate](ci.md#ci-the-merge-gate)). Before a merge, the author runs the flows of the journey the change touches on a physical Android phone connected over USB and attaches the result (Maestro output, screenshots, the installed `versionCode`) to the task. On Zhafron's PC that phone is the Meizu Mblu 21.

- Pick the phone explicitly: export `ANDROID_SERIAL` (from `adb devices -l`) and pass `maestro --device "$ANDROID_SERIAL"`; `scripts/e2e-android.sh` already forwards it. Never let Maestro take the first device, which may be the emulator.
- One session at a time: take a `flock` on one lock file per phone for the whole session (install, flows, restore) and release it when done, as `scripts/emulator.sh` does for the emulator. On Zhafron's PC the lock file is `~/re/mblu21/.phone.lock`.
- Install only the APK under test, with `adb install -r`. Never `pm clear` the app, wipe data, or uninstall other apps on the phone. Note the installed `versionCode` first, pull its `base.apk` (`adb shell pm path io.kaitech.mobile`), and reinstall it when done.
- A change without native changes (native fingerprint unchanged) needs no native build: repack the branch's JS bundle onto the installed APK with `npx repack-app --platform android --js-bundle-only --source-app base.apk`, signed with the release keystore, and set `APP_BUILD_NUMBER` to the installed `versionCode` so the install keeps the app's session. A native change uses the arm64 APK of a CI build of the branch (`gh workflow run ci.yml --ref <branch>`) or of `main`.
- Accounts: a flow that needs a signed-in session never signs in with Zhafron's account or with a CI test account; the device cleanup before every signed-in CI cell revokes the idle phones of the CI accounts (see [Test accounts](ci.md#test-accounts)). Run signed-out flows, or flows that start from the session already on the phone without changing it.
- The phone is shared with its owner: unlock it only when it is idle and never type its PIN from a script without reading the screen first. Answer system prompts the install raises (Play Protect asks to scan an unknown app) without changing settings.
- Frame pacing of the composer: `node scripts/phone-jank.mjs --thread <channelId> --scenario record-cancel,attach,record-lock [--apk main=<apk> --apk branch=<apk>] [--rounds 3] [--repeat 5] [--max-janky 5] [--max-p90 11.1]` opens the thread, runs each scenario once to warm up, resets `dumpsys gfxinfo`, repeats it, and prints the janky share, p90, p99 and GPU p90 per build and scenario. With several `--apk` builds it installs them in turn and reverses the order every round, so neither build is always measured first. `record-cancel` holds the mic for 2.5 s while sliding left, `attach` opens and closes the attach sheet, `record-lock` slides up to lock, then pauses, plays, stops and discards the draft. It exits 1 when a build is over a limit. Run it inside the phone lock, never while `screenrecord` runs: recording the screen inflates jank on the Mblu 21 (60-88% instead of 21-34% for the same build).

Push on the phone (ZHA-7944): `.maestro/local/push-message-open.yaml` kills the app, has the web account post through lab0 (`web-peer.js` `say`), opens the notification shade and taps the notification, and expects that conversation with the message; `.maestro/local/push-call-answer.yaml` kills the app, rings it from the web account (`ring`), declines from the notification, rings again, answers, and expects the call screen. Both need a phone signed in to the account that `CHANNEL_ID` (a direct chat with the web account) belongs to: `maestro --device "$ANDROID_SERIAL" test -e SERVER=... -e DB=... -e WEB_LOGIN=... -e WEB_PASSWORD=... -e CHANNEL_ID=... -e RUN=E2E$(date +%s) -e DEVICE_SIZE=phone -e ORIENTATION=portrait -e APP_LANGUAGE=id .maestro/local/push-*.yaml`. They cannot run in CI: an emulator in CI has no Google Play services to receive FCM. `scripts/push-latency.mjs <message|call|activity> <count>` with `PUSH_STATE=background|swiped|stopped` measures delivery per trial from the phone's system event log (`notification_enqueue`), the numbers in [Releases](releases.md#android-push-on-a-physical-phone-zha-7944).

## Device matrix

The superapp must be responsive on phones and tablets, Android and iOS, portrait and landscape. Every Android cell is its own job with its own emulator, so all eight cells run in parallel.

| Platform | Size | Device | Window width portrait / landscape | Orientation | Language | Status |
|---|---|---|---|---|---|---|
| Android 15 (API 35) | `phone` | emulator profile `pixel_6` | 411 dp (compact) / 914 dp | portrait, landscape | `en-US`, `id-ID` | must be green |
| Android 15 (API 35) | `tablet` | emulator profile `pixel_tablet` (10 inch) | 800 dp (medium) / 1280 dp (expanded) | portrait, landscape | `en-US`, `id-ID` | must be green |
| iOS (latest simulator runtime on the `macos-26` runner) | `phone` | newest available iPhone simulator (iPhone 17 Pro, then iPhone 17, 16 Pro, 16) | see `simulator.txt` | portrait, landscape | `en-US` | job `ios simulator en-US` in the full `E2E` run (nightly, manual), not a merge gate; the Maestro XCTest driver gets a 10-minute start timeout (`MAESTRO_DRIVER_STARTUP_TIMEOUT=600000`) and the cell is retried once only when it fails with `IOSDriverTimeoutException`; the driver is built from the pinned Maestro source with `scripts/maestro-ios-runner.patch` (`scripts/maestro-ios-runner.sh`, cached per Maestro version and patch), because stock Maestro lets any issue XCTest records inside `testHttpServer` (an accessibility element that vanished while the status bar is read, mobile-dev-inc/Maestro#3538; the 30-second orientation timeout of ZHA-7557) end the test and with it the driver's HTTP server, failing the rest of the cell with `DeviceUnreachableException`; the patched driver logs the issue (`XCTest issue kept out of the test run`) and keeps serving |

Android orientation is set through `user_rotation`, taking the panel's natural orientation into account (tablets are naturally landscape); the iPhone simulator uses Maestro's `setOrientation: LANDSCAPE_LEFT` in the `onFlowStart` hook (`.maestro/shared/orientation.yaml`) for landscape cells, because the Maestro XCTest runner returns the simulator to portrait on every new session. Portrait cells make no orientation call there: the session already starts portrait, yet XCTest still waits up to 30 seconds for the confirmation of a change that does not happen (30.9 and 68 seconds at the start of a cold session, ZHA-7557). A flow that turns the screen away from the cell orientation turns it back itself. Every new flow must include that hook:

```yaml
onFlowStart:
  - runFlow: shared/orientation.yaml
```

On Android the hook does nothing. The panel size, density, and rotation of each cell are recorded in `display.txt`. The iPhone simulator needs no signature or Apple account. The iPad simulator is not tested since ZHA-7503 (its job took 32 to 71 minutes and held every run behind it); a real iPad or iPhone has not been tested.

Screenshots are named `<screen>-<size>-<orientation>-<language>.png`, for example `launch-tablet-landscape-id.png`, through a shared subflow:

```yaml
- runFlow:
    file: shared/screenshot.yaml
    env:
      SCREEN: launch
```

Every cell screenshot is copied to `screenshots/`. `scripts/check-screenshots.mjs` fails the cell when a screenshot does not follow the name pattern or its dimensions do not match the cell's orientation (for example a screen locked to portrait in a landscape cell). iOS screenshots are stored in a portrait frame with an EXIF orientation tag; the check uses the dimensions after that tag is applied. Flows in the `.maestro/shared/` subfolder are not run on their own.

## Tablet configuration gate

`node scripts/check-tablet-config.mjs` (a CI step in the lint job) fails when `orientation` is not `default`, `ios.supportsTablet` is not `true`, `ios.requireFullScreen` is `true`, or the `expo prebuild` output locks `android:screenOrientation`, turns off `android:resizeableActivity`, turns on `UIRequiresFullScreen`, or does not support all four iPad orientations.

The sign-in to sign-out flows live in `.maestro/signed-in/` and are not part of `maestro test .maestro` in CI, because they need a test account and a build with `KAITECH_LINK_HOST` and `KAITECH_DEFAULT_DB`; these flows sign in to the default server. Run them with `maestro test -e APP_LANGUAGE=id -e DEVICE_SIZE=phone -e ORIENTATION=portrait -e LOGIN=<account> -e PASSWORD=<password> .maestro/signed-in`; never write those values to the repo, logs, or public artifacts.

The `signed-in/discovery.yaml` flow signs in when needed, then opens the Programme home, findings and their evidence, asks the Coworker (on an Android phone the screen is rotated in the middle of typing to prove the draft survives), decision cards when one is waiting, combined search, and Activities. Extra variables: `-e QUESTION=<question> -e SEARCH=<word>`. Run it only with a test account that is a member of test Programmes only; the recording shows the Programme contents.

The `signed-in/discovery-sections.yaml` flow signs in only when the app is signed out, opens All sections from the Programme home, the Programme detail and its More sheet, Knowledge, one section from every web menu group (list, first record, More sheet), then creates a new Glossary term and taps Accept. Extra variables: `-e TERM=<unique term>` and `-e PROGRAMME=<test Programme name>` (picked in the Programme picker first); the flow creates data in the open Programme.

The `signed-in/discovery-all-sections-1.yaml` to `-3.yaml` flows open every web Discovery menu the test account can see (64 menus, split in three so one emulator crash does not lose the whole run), wait for the list, and open the first record; no step changes data. `signed-in/discovery-actions.yaml` taps Pause, Resume and Snooze Proactive on the Programme, checks that accepting a RAID without evidence is refused by the server with its reason, rejects one RAID, and posts a note on a Department; variables `-e NOTE=<text> -e RAID_ACCEPT=<RAID name> -e RAID_REJECT=<RAID name>`. `signed-in/discovery-decisions.yaml` accepts and rejects a Department and rejects a Glossary term; variables `-e DEPT_ACCEPT= -e DEPT_REJECT= -e TERM_REJECT=` hold names of test records still in Draft. Every record these flows use must be test data you created in a test Programme.

`themed/tour.yaml` photographs Chat, the row More sheet, Discovery, MoM, Activity and Settings as `<theme>-t<n>-<screen>-<size>-<orientation>-<language>.png`; `scripts/e2e-android.sh` runs the flows in `E2E_THEMED_FLOWS` once with `adb shell cmd uimode night no` and once with `yes`, so the theme changes on the emulator and not in the account's Appearance setting, which parallel cells share. `themed/dialogs.yaml` then opens the sign-out confirm and closes it with the back button (`<theme>-d1-confirm-destructive`), the camera card before the system prompt (`<theme>-d2-permission-card`, launched with the camera denied) and the snackbar of a too-short voice note (`<theme>-d3-snackbar`); it asserts the app's testIDs and that no `android:id/button1` system dialog or permission controller is on screen. Before every tap and screenshot it waits for an incoming call from another job to go away (`shared/no-ring.yaml`) and never declines it. `E2E_SCROLL_FLOW` (`themed/scroll.yaml`, after `scroll-ready.yaml` opens the list) swipes the Chat list six times down and up between a `dumpsys gfxinfo` reset and dump and saves `scroll-gfxinfo.txt`. The rows job sets both through the `themed-flows` and `scroll-flow` inputs of `.github/actions/android-e2e`.

`E2E_MOTION_FLOW` is the path prefix of three flows (`signed-in/chat-motion`): `-ready.yaml` opens the chat with `PEER`, then `-send.yaml` (eight messages, each waiting until the queued bubble is gone) and `-fling.yaml` (six fast flings towards older messages and three back, so the list never reaches its newest message, where Android draws its overscroll stretch) are each recorded on screen, and `scripts/frame-flicker.mjs` compares every frame of the thread list with the one before it after removing the scroll offset. A frame whose content changes by at least 1% of the list and returns to the earlier picture within 350 ms while the list stands nearly still is a flicker; a frame with a quarter of the list empty is a blank frame, and one with half of it empty a half-blank frame. The send phase fails when it has more than `E2E_MAX_FLICKER` flickers (default 0), the fling phase when it has more than `E2E_MAX_HALF_BLANK` half-blank frames (default 0); it reports blank frames without failing on them. A quarter was the first limit, but on the CI emulator the new app drew up to 7 such frames in a fling (runs 45736699363, 45739424357), more than the 6 of the old app in run 45610143374, so no count of them separates the builds. The emulator draws a frame every 100 to 250 ms, so a fast fling outruns the rows that are ready: with the new app those frames are single and between 36% and 42% empty (run 45764830890, on the three flings back towards the newest message), while the old app empties the whole list for up to 13 frames in a row, 26 of its 29 blank frames at least half empty (run 45764834404). On the Mblu 21 the same split holds: 0 half-blank frames after and 223 before (the scroll recordings of ZHA-7803). The fling phase reports its flicker count without failing on it: on the CI emulator it was 1 and 0 for both the old and the new app (runs 45610143374 and 45610107276), and the flagged frames inspected on the Mblu 21 were Android's overscroll stretch at the ends of the list, not redrawn rows, while blank frames separated the builds (6 and 23 before, 0 and 0 after). Eight sends, not three, because on the CI emulator the old send flicker appeared in one of two cells with three sends (run 45573400573). The phone cells of `android chat` set it through the `motion-flow` input. The recordings are pulled into a temporary folder outside the output and deleted after the check, so only `motion-<phase>-flicker.json` (with the time and empty share of every blank frame in `blankAt`), `motion-<phase>-flicker.txt` (with the flow duration), `motion-<phase>-gfxinfo.txt` and the first twelve blank frames as `failures/motion-<phase>-blank-<ms>ms.png` are uploaded; the cleanup keeps those three exact name patterns and `failures/`, never a wildcard that a video could match. A phase whose flow runs longer than the 170 s recording fails, because its end was not checked. Locally: `node scripts/frame-flicker.mjs <video.mp4> <left,top,right,bottom> [--blank-frames dir] [--max-flicker N] [--max-blank N] [--max-half-blank N]` (a limit left out is not checked) with the `thread-list` bounds from `uiautomator dump`; it needs `ffmpeg` and `ffprobe`.

The rows job also sets the `layout-check` input: after its flows, `scripts/e2e-layout.mjs` stops the Maestro driver and, through `adb` and `uiautomator dump`, opens Chat, Discovery, MoM and Activity in turn and fails the cell when the title, Search and profile are not in one bar row, the bar is not 56 to 64 dp tall, there is space between the status bar and the bar, the first content starts more than 24 dp under the bar, Search or the profile is cut off, or the pull to refresh indicator is clipped or reaches into the bar at any of six pull depths from 16 to 128 dp (`input motionevent` holds the finger down while each dump runs). It then posts a short and a long message from each side of the conversation with the web account (`E2E_CHANNEL_ID`) through the server, opens that conversation, and fails the cell when a bubble is wider than 80% of the message lane, a short bubble is not sized to its text, a long one did not wrap at that cap, or a bubble leaves its side (yours right, theirs left) (ZHA-7809), or the composer of that conversation ends less than 8 dp above the navigation bar (ZHA-7854). It writes the measurements to `layout.txt` and the screenshots `layout-<tab>-*.png`, `layout-bubbles-*.png`, and `pull-<tab>-*.png` (fully pulled). The same script runs on a physical phone: `node scripts/e2e-layout.mjs <dir> phone portrait id` with the app signed in and in front (ZHA-7730).

The Chat flows (`signed-in/chat.yaml`, `signed-in/message-actions.yaml`) are described in [Architecture: Chat](architecture.md#chat-srcfeatureschat), the row action flows in [Architecture: Row actions](architecture.md#row-actions-srcuirowactionstsx), and the call check in [Calls](calls.md#trying-a-call-from-this-machine).
